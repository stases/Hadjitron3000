# Architecture

Hadjitron 3000 is a web app (TypeScript, React, the Web Audio API) inside a thin Electron shell. Everything that makes sound runs in Chromium's audio engine, so the app behaves the same in Electron on a Mac, in Electron on Windows and in a Chromium browser, which is also where the tests run.

## Layout

| Folder | What lives there |
| --- | --- |
| `src/core` | The document model, the module table, the sequencer and the file formats. Pure TypeScript, no DOM and no audio. |
| `src/audio` | The Web Audio engine, the transport, offline rendering and MP3 encoding. |
| `src/state` | The app store and its actions, including undo. |
| `src/platform` | Files, the sound and block library folders and the window, once for Electron and once for the browser. |
| `src/app` | The window chrome, dialogs, keyboard shortcuts, MIDI input, recording, the stored session, the Guide Book and its guided steps, and the glue between store, engine and platform. |
| `src/ui/kit` | The retro widgets. `src/ui/theme` holds the tokens and fonts. |
| `src/ui/factory`, `src/ui/track`, `src/ui/song`, `src/ui/mixer` | The four views. |
| `src/presets` | Factory sounds in the app's own file format, the demo project, the six example songs, and the factory blocks taken from them. |
| `electron` | The main process, the preload script and the two updaters, plain CommonJS with no build step. |
| `tests` | `unit` runs in Node, `browser` runs in headless Chromium (the engine needs real Web Audio), `e2e` drives the built app. |

Dependencies point one way: `core` knows nothing else; `audio` and `state` use `core`; `app` and `ui` use everything. The views never talk to the engine directly; they read the store, call actions, and use the small audio controller in `src/app/audio.ts` to audition notes.

## The document

A project (`Project` in `src/core/types.ts`) has a tempo, a swing amount, a time signature, a master level, a mixer, a list of channels, a list of blocks, a song and the audio files it uses. A channel is one row of the Track grid: a sound plus mute, solo, two sends and its ducking. The Factory, the Track and the Mixer are views of the same channels, so a sound made in the Factory is immediately a row on the grid and a strip in the Mixer.

The mixer (`Mixer`) holds two send buses and the master's effect chain. A bus (`SendBus`) has a name, an effect chain, a level in decibels (its bottom, -48 dB, is silence) and a mute. A channel's `sends` say how much of it, 0 to 1, goes to bus A and bus B, taken after its level, pan, mute, solo and ducking. Its `duck` names another channel (`source`, or null), an `amount` (how far it dips, as a share of full level) and a `release` in seconds: every note the source starts dips the channel's level, dry signal and sends alike, which then recovers. A new project's buses are a Room with a reverb and an Echo with a delay, both fully wet (`defaultMixer` in `src/core/defaults.ts`), and every channel starts with its sends at 0 and no source (`newChannel`). Sends and ducking belong to the channel, not the sound, so sound and block files carry neither. The store's chain actions (`addEffect`, `moveEffect`, `removeModule`, `setModuleOn`, `setParam`) take an `Owner`: a channel id for a sound, or `{ rack }` for a bus (0 or 1) or the master; an effect added to a bus starts fully wet. The ranges and levels of the mixer's own controls are in `src/core/mixer.ts`: sends, bus faders and the bus racks are Basics, ducking and the master rack Shaping.

The Mixer view (`src/ui/mixer`) puts a strip per channel, the two buses and the master in one CSS grid whose rows every strip shares (`subgrid`), so knobs, faders and buttons line up whatever a strip holds, and a column of captions stays at the left while the strips scroll sideways. The rack under the strips is the Factory's: `EffectChain` in `src/ui/factory/Rack.tsx` draws the units of any chain with its add list, move and remove buttons and level folds, and the controls in `controls.tsx` take the same `Owner` as the store.

What the user sees as a block is a `Pattern` in the code, and the store keeps that word in its names (`patternId`, `addPattern`, `renamePattern` and so on). A block has a name, a colour, one to thirty-two bars, and for each channel a list of notes (`Pattern.notes`); a project holds up to 26 blocks. A note (`Note`) has an id that is unique within its block, a start and a length in ticks, a pitch and a velocity, and four optional extras that are absent while they have their default value: `chance` (1 to 99, the percent of passes it plays on), `ratchet` (2, 3, 4, 6 or 8 repeats inside its length), `slide` (the pitch glides in from the row's previous note) and `hold` (a drone to the end of its placement). `noteExtras` in `src/core/notes.ts` keeps them valid, and `cleanNotes`, the file reader and the store's note edits all go through it, so a default value is never stored or written. Notes may also carry locks, below.

The time signature (`Project.meter`) is `[beats, unit]`, one of 2/4, 3/4, 4/4, 5/4, 6/4, 7/4, 5/8, 6/8, 7/8, 9/8 and 12/8, and holds for every bar of every block. `barOf` in `src/core/meter.ts` is the one place that turns it into a bar: `beats * 16 / unit` steps, their ticks, and the steps on which its beats start (four steps to a beat in x/4, six in 6/8, 9/8 and 12/8, and in 5/8 and 7/8 four with a beat of six last). Block lengths, the sequencer, the grid's and the roll's columns and backgrounds, positions as bar.beat.sixteenth, the Song's bar width and the status bar all ask it. Changing the meter (`setMeter`) keeps every note at its tick and gives each block the fewest bars of the new meter that hold its old length and the notes that start in it; placements keep their bars. A step has 24 ticks (`TICKS_PER_STEP`, 96 to a quarter note), so a 32nd is 12 ticks and a sixteenth triplet 16. A row's notes are kept sorted by start and then pitch; they may overlap, and several may start together as a chord, but no two share both start and pitch. Note 60 is C3 and plays a sound at its own pitch.

A project may have a scale (`Project.scale`, absent while the project is chromatic): a root from 0 (C) to 11 and one of the types of `SCALES` in `src/core/scale.ts`, where `inScale`, `nearestInScale` (the nearer scale note, the lower of two as near) and `scaleNotes` live. The scale changes no note by itself. The roll shades the rows outside it and marks the root (`sheetBackground` takes the scale), and while the preference Snap to Scale (`scaleSnap` in `src/app/prefs.ts`) is on, `snapPitch` and `stepPitch` in `src/app/snap.ts` put on it the notes the roll adds and drags, the grid's pitch drags and arrow keys, recorded notes and notes typed into a step. The store's `fitToScale` moves chosen notes of a row onto the scale in one change, a note that lands on another of the same start and pitch merging into it.

A block may give a row a loop of its own (`Pattern.loops`, channel id to steps, absent when no row has one): the notes that start inside that many steps play over and over, end to end, for the length of the block, and the row's notes after them stay in the document, silent. A loop is shorter than its block; `setRowLoop` takes away one that is not, and so do `setPatternBars` and `setMeter` when the block becomes as short as it. A copied block keeps its loops, a block in the library carries its row's as `loop` on the track, and `removeChannel` drops the channel's.

`randomNotes` in `src/core/randomise.ts` draws notes for a stretch of ticks from a seed through `hash` in `src/core/hash.ts`, so the same seed and settings always give the same notes: grid lines that start again with every bar, the density's share of them chosen by the seed, pitches of the scale (all twelve without one) in a range around a centre, and lengths, velocities, ratchets and chances varied as far as asked. The Randomise dialog (`src/ui/track/RandomiseDialog.tsx`) writes the row with `replaceNotes` and a take of its own (see Undo), so every Apply while it is open, each in place of the one before, is one undo step.

The Track's step grid shows a row's notes by the step they start in. A cell with more than one note shows the lowest one and how many more; a note that starts between grid lines gets a small mark at its place in the step. The grid and the roll mark a note's extras the same way (`src/ui/track/marks.tsx`), and the inspector under them sets extras on every selected note at once; in beginner mode it folds them by level with the Factory's fold toggles (`FoldToggles` in the kit and `useShown` in `src/ui/factory/levels.tsx`). The grid's gestures act on all the notes that start in a cell, so material the grid cannot draw on its own survives ordinary editing.

The piano roll (`src/ui/track/PianoRoll.tsx`) shows one row of the block over pitch and time in the grid's own columns at one pixel per tick, so every note is exactly where it plays; its geometry, snapping, hit-testing, drags and clipboard are pure functions in `roll.ts`, and its open state, selection, snap and paste mark live in a small store of its own (`rollState.ts`) that the global key handler also uses. Notes and velocity bars are plain absolutely placed elements and the sheet's rows and columns are one repeating CSS background, which stays cheap for a few hundred notes. A drag keeps its result as a local draft and writes it once on release with `updateNotes`, so a selection dragged over another note never stops halfway, and paste and repeat add their notes in one change with `addNotes`.

The song is a list of placements (`Placement`): a block put on one of four lanes at a bar, for a number of bars. Placements in different lanes play together; in one lane they never overlap. A placement longer than its block repeats it, and a shorter one cuts it off. The Track edits one block and the Song arranges them.

A placement has three optional fields that are absent while they have their default value: `fadeIn` and `fadeOut`, whole bars that together fit inside it, and `mutes`, the ids of the channels that are silent in it, in channel order. `fitFades` in `src/core/arrangement.ts` keeps the fades inside their placement, the fade-in first; the store goes through it when fades are set, when a placement is made longer or shorter and when it is duplicated, and the file reader does too. A resize drag hands the fades it started with back to the store after every step, so a tile dragged shorter and longer again in one gesture keeps them. `Project.lanes` holds one `Lane` per lane of the song, a level in dB from -48, which is silence as in the Output unit, to +6, and a mute. Lane levels, fades and mutes apply only to the song; the block on repeat plays as it is. A lane's level and mute are Basics; a placement's fades and mutes are Shaping, which beginner mode folds behind a toggle in the placement bar (`useShown` and `toggleFold` with the type `placement`).

`Project.automation` holds the song's rows of automation (`AutoRow`): an id, the parameter it moves (`ParamRef`) and its points. A `ParamRef` names a parameter the way the store's chain actions do: an `owner` (a channel id, or `{ rack }` for a bus or the master), a `module` and a `param`. In a sound the module is `source`, `play`, `filter`, `amp`, `out` or an effect's id, and the module `send` with the parameter `0` or `1` is the channel's send to that bus; in a rack it is an effect's id, or `out` with `level` for the bus's or the master's level. A point is `[tick, value]`, the value 0 to 1 through the parameter's knob taper (`toNorm` and `fromNorm` in `src/core/params.ts`), so a row keeps its shape when the parameter's range is read in other units. Between points the value runs in a straight line in that 0..1 space, it holds the first point's value before it and the last point's after it, and a row without points moves nothing. A row's value in the song is `pointsValue` at the tick modulo the song's length. Rows never change stored values, so the knobs keep what the user set and Stop puts it back. Choices, switches (such as the space's Freeze), the reverb's size and tone, which rebuild its impulse, and the arpeggiator's octaves and gate, which the sequencer reads before the engine sees any note, cannot be automated or locked (`FIXED` in `src/core/automation.ts`). That file also lists what can be (`soundTargets` and `automationGroups`, in the picker's order) and says what a row or a lock names (`refSpec`, `refLabel`); the store's `addAutomation`, `removeAutomation` and `setAutomationPoints` edit the rows, and removing a channel or a module, or changing a source's type, drops the rows whose parameter is gone (`dropStaleAutomation`).

A note can also carry up to two locks (`Note.locks`, `Lock`): a parameter of its sound, named by module and parameter like a modulation target, and a value 0 to 1 through its taper. A lock of a parameter inside the voice (source, play, filter, amp) gives that note's voice its own value; a lock of a shared one (an effect, the output) sets it from the note's start to its end, and a later note's lock wins while both sound. Locks go through `noteExtras` like the other extras, `validLocks` drops those whose parameter the sound no longer has on the next edit of the note, and the engine ignores them meanwhile. The store's `setNotesLock` sets one slot of the selected notes; a lock of the same parameter in the other slot gives way.

A block can also stand on its own outside a project (`Block`): its notes together with the sounds that play them and their samples. It has no time signature of its own; its bars count in the meter of the project it is in. `extractBlock` in `src/core/block.ts` lifts one out of a project, and the store's `insertBlock` adds one to a project, reusing a channel when the project already has the same sound. The Block Library offers the blocks of the demo song and of the examples this way, grouped by song, and the user's own blocks from the block library folder.

A sound is a source, a filter, an amp envelope, a chain of effects, a set of modulators and an output, together with how its notes follow each other (`play`: Poly, Mono or Legato, a glide time, and the arpeggiator, see Time):

```
     inside every note                         shared by all notes
source -> filter -> amp envelope  ---+--> effect -> effect -> ... -> output (level, pan)
                                     |
modulators (envelopes, LFOs, drifts) -> any parameter marked as a target
```

Source, filter and amp envelope are built for every note; the effects and the output exist once per sound. The filter (`sound.filter`, the `FILTER` definition) is part of every sound and off by default; its lamp is the parameter `on`, which the Factory draws as the unit's lamp rather than as a control. A modulator (`ModInst`) has `per`: with `'note'` it is built inside every note as well and may only move parameters that live there, the source's and the filter's (`perNote` in `src/core/modules.ts` decides); with `'sound'` it exists once and may move anything. Files without the field read as `'sound'`, which is how modulators worked before.

A drawn wave is one cycle of 64 points in -1..1 (`src/core/shape.ts`), kept in the source's parameters `shape` and `shape2` as a string of two base-64 digits per point, so the parameter model (number, string or boolean) stays as it is; the choice Draw of `wave` or `wave2` plays it. Parameters that a file lacks read as their defaults, so sounds from before keep their meaning: LFOs run free without fade or retrigger, and each oscillator has a sine to draw from.

Every module is described once in `src/core/modules.ts`: its parameters with ranges, units, knob tapers and defaults. The engine, the file format and the generic module panel in the Factory are all driven by that table. Every module and parameter also has a level from `src/core/levels.ts` (Basics when absent), which the Factory uses in beginner mode to fold Shaping and Deep controls into sections and to group the add lists; it is a property of the table only and never reaches the file format or the engine. The beginner/pro switch is a user preference in `src/app/prefs.ts`, kept in localStorage rather than in the project. Parameter values are stored in real units (hertz, seconds, semitones, decibels).

## Files

Sounds are saved as `.h3s`, blocks as `.h3b` and projects as `.h3k`. All three are JSON text with a `format` tag and a `version`. Audio files used by a sampler are embedded as base64 in their original encoding and are keyed by a hash of their content, so the same file is stored once however many sounds use it. `src/core/fileformat.ts` reads and writes the three formats and refuses files it does not understand with a readable message. The current version is 3. Projects of version 1, whose song was a list of patterns played one after another, open with that list laid out in the first lane. Versions 1 and 2 kept one step per row and step index (`cells` in a project, `steps` in a block) with a length in steps; reading them, and a stored session of that age, turns step i into a note at tick 24 i and its length into ticks, so nothing is lost. Only version 3 is written. A project always carries its `meter`; one without it, from before time signatures, opens in 4/4. A project without `mixer`, or channels without `sends` and `duck`, from before the mixer, opens with the default buses, sends at 0 and no ducking, and so sounds exactly as it did; a duck source that is not another channel of the project is dropped. Notes carry their extras only when they are set, in projects and blocks alike. A project carries its `scale` only when it has one, and a scale it does not know is dropped. A block carries `loops` only when a row has one, of the channels it has, in whole steps. A sound always carries all of its play settings, the arpeggiator's included, as it carries every parameter; a sound from before the arpeggiator reads with it off. A project always carries its `lanes`; one without them opens with every lane at 0 dB and playing. Placements carry `fadeIn`, `fadeOut` and `mutes` only when they are set; mutes of channels the project does not have are dropped. Blocks carry none of these. The sampler's `xfade`, `slices` and `sens`, the Grains source and the parameters of the new effects follow the same rule as every parameter: a file without them reads their defaults, and the defaults leave the sound as it was. A project always carries its `automation`, empty or not; one without it opens with none. Rows whose parameter the project does not have, or a second row of the same parameter, are dropped, and points are sorted and kept within the longest song there can be, their values within 0..1. Notes carry `locks` only when they have any, in projects and blocks alike, and locks of parameters their sound lacks are dropped. None of this changed the version.

## The engine

`Engine` (`src/audio`) owns one audio graph and one strip per channel, the two send buses and the master:

```
voices: source -> filter (stage, drive, stage) -> [gain curve] -> voice gain (amp envelope x velocity) --+
                                                                                        +--> effect chain -> output
                                                                                        |      -> channel gain (mute/solo) -> strip
per-note modulators -> (fade) -> depth gains -> parameters of their own voice
modulators of the whole sound -> (fade) -> depth gains -> audio parameters, those inside the voices included
strip: ducking gain -+-> sum
                     +-> send A -> bus A: its sends summed -> effect rack -> level and mute -> sum
                     +-> send B -> bus B: ...
sum -> master rack -> master level -> soft clip -> destination and analyser
```

Each channel also has a tap of its own output ahead of mute and solo, made the first time the Factory's scope reads it.

The strips, the buses and the racks are in `src/audio/buses.ts`; `channel.ts` knows nothing of them. A strip (`Strip`) lives as long as its channel, so a sound whose graph is rebuilt keeps its sends and its ducking. A bus (`SendBusGraph`) sums the sends of the channels from the start, but builds its rack, level and mute, and takes its place in the sum, only the first time a channel sends to it; a bus nobody sends to costs nothing and adds nothing. A rack (`EffectRack`) is a chain of effects made by the sound's own effect builders with `shared` set. Every Mix knob goes through `blend`, which crossfades from dry to wet, so 100 % gives the effect alone; only the delay and the reverb ask it to add their wet on top of the untouched dry instead, as they always have in a sound, and `shared` turns that off on a bus or the master. Space, which mixes inside its processor, does the same through a `dry` parameter of its own, 1 in a sound and 1 - Mix when shared; the other processor effects always crossfade. A compressor in a rack has its reduction meter like one in a sound (`Engine.effectReduction` takes a channel id or a rack). An empty rack is a gain of one, and a gain of one leaves every sample as it is, so a project that sends nothing renders bit for bit as before the mixer. When a rack's structure changes, the new one is built beside the old and they crossfade in about 30 ms. Meters in the Mixer read small analysers made on a strip or a bus the first time they are read, and only while the Mixer is on screen.

Ducking has no detector: `Engine.play` and `Engine.noteOn` tell the strips that duck to the channel, and each schedules its gain at the note's time to fall to 1 - amount in 5 ms and rise back in a straight line over the release. A strip keeps the corners of its curve and the notes still to come, so a live note between scheduled ones is laid in without losing them. It is driven by notes, so it renders offline exactly as it plays, and a muted source still ducks.

Each note is a voice with its own source, filter, amp envelope and per-note modulators; nothing is built for a part that is switched off (the filter off, the sub or the second oscillator at 0, no per-note modulators), so a sound made before the voice path plays bit for bit as it did.

A note can bring a gain curve (`NoteEvent.gain`, passed on by `Engine.play`): breakpoints in seconds from the note's start with a linear gain, which the voice follows with a gain stage of its own in straight lines from point to point (`follow` in `src/audio/automation.ts`), holding the last value through the release. The stage starts with the amp envelope, after the filter's drive delay. When a slide or Legato ties a new note into a sounding voice that has such a stage, the stage takes over the new note's curve from that moment, or goes back to full gain when the new note has none. A note without a curve builds no stage, so a song without fades and with every lane at 0 dB renders exactly as before. The effect chain and the modulators of the whole sound are shared by all voices of a channel; such a modulation envelope restarts on every note and follows the most recent one.

What a modulator plays before its depth comes from `src/audio/modules/modulators.ts`. An envelope is a constant source whose level the channel schedules, as before. An LFO is an oscillator followed by a gain for its fade-in. With Sync its frequency is one cycle per note value at the tempo (`lfoRate`), and `ChannelGraph.update`, which gets every change of tempo, moves it, in the LFOs of the whole sound and of the sounding notes alike. The fade gain rises in a straight line from 0 to 1 from the start of a note; for an LFO of the whole sound every new note dips it to 0 in 5 ms and starts the rise again, and Retrigger replaces its oscillator with a new one started at the note, since an oscillator's phase cannot be reset. An LFO in every note is built with its note, so it always starts there.

A modulator of the whole sound that moves a parameter inside the voice is summed once and connected to each voice as it is built. Chromium runs only the nodes that something pulls, and an oscillator or a buffer it does not run stands still, so such a modulator moves on only while a voice pulls it. An oscillator or a sampler pulls exactly while it plays, so an LFO on the pitch, the pulse width or the FM amount moves on only while notes sound, as it always has. The voice filter and the grains processor go on pulling for a while after their note, until the page hears that the voice has ended or Chromium lets them go, and the load of the machine makes that sooner or later; through them alone an LFO would stand still for a different time in every render. So a modulator of the filter's cutoff, or of anything in a grains voice, also feeds a silent gain into the channel's output, which keeps it running all the time. Every parameter inside a voice gets one connection: the note's own modulators and the summed ones of the whole sound are added up first, because a parameter adds each connection to its own value in an order that changes from run to run, and with two of them the last bits of an export would differ (see `src/audio/mix.ts`).

Drift is a looping buffer of 4096 random values in -1..1, 64 samples each at a nominal 3 kHz, read by an `AudioBufferSourceNode` at a speed that passes `rate` values a second. Smooth decides the buffer: every value holds for the first (1 - smooth) of its cell and glides along half a cosine to the next in the rest, so 0 is sample-and-hold and 1 glides all the time. All settings share the same values, so a change of Smooth crossfades over 30 ms to the other buffer at the same place, which the drift computes from where and how fast it has been reading. Each drift starts at its own place in the loop, from the engine's voice counter (`serial`) times the golden ratio, so notes wander differently, a render is the same every time, and at the fastest rate the loop takes nearly seven minutes to come round. The buffers are built once per setting and shared by every context.

A drawn wave is a `PeriodicWave` of 512 harmonics. Joining the points with straight lines gives the points' own spectrum, repeated every 64 harmonics and multiplied by sinc² (`shapeHarmonics`); the oscillator leaves out whatever would lie above Nyquist at the note's pitch, as it does for the stock waves, and plays the drawing at the level it was drawn, without its constant. The last few waves are cached per context by their string. A drawn wave plays on two oscillators started together, one of them silent; a new drawing goes into the silent one, which then takes over with a 5 ms crossfade, so a held note follows the drawing without a click. The Factory sends a drawing to the store, and so to the engine, at most every 100 ms while the mouse moves, and once more when it is let go.

The oscillator's pulse width is a sawtooth minus the same sawtooth delayed by the width's share of a period (`pulse` in `src/audio/modules/sources.ts`). Both are band-limited, the delay moves smoothly when the width is modulated, and at 50 % the result is the square wave harmonic for harmonic. A square at 50 % that no modulator moves is still the plain square oscillator.

Glide is a straight line in cents on the parameters that follow the voice's pitch (`Follower`): the oscillators' detune, the filter's detune as far as key tracking says, and the pulse delay, whose period changes by the matching exponential ramp. In Mono a new note starts a new voice and releases the old one within 5 ms; in Legato, and for a note played with `slide` (`Engine.play`), the sounding voice is moved to the new note instead, and its envelopes go on as if the key had stayed down (`envelopeSegments` with a starting time). The channel keeps the live keys that are down, so in Mono and Legato letting go of the newer key goes back to the older one. The filter's drive is an oversampled wave shaper that delays the sound by 128 samples; the amp envelope of such a voice starts as much later, so the attack is not lost.

Automation reaches the engine as points through `Engine.automate(ref, value, time)`: the parameter, in its own units, should arrive at `value` at `time` in a straight line from the point before. The channel, the strip, each bus, each rack and the master level keep the points of their automated parameters (`Automated` and `Curve` in `src/audio/automation.ts`), and while a parameter has a curve, `setProject` leaves it to the curve: an effect's `update` gets the curve's value at that moment over the stored one (`overlay`), and the glides of the output, the sends and the bus and master levels are skipped. Levels, pans, sends and the master level are ramped directly. An effect moves through its optional `ramp`: every stock effect has one. Those of stock Web Audio nodes get it from `ramped` in `effects.ts`, which runs the effect's own `update` twice while `glide` only notes what it would set, once for the new value and once with the parameter moved, and ramps the AudioParams that differ (`rampWith`); those made of a processor (the crusher, the comb, the tape and the space) get it from `processorEffect` in the same way, so the ConstantSourceNodes that feed the processor's parameters ramp. An effect without `ramp` is stepped through `update` instead, each time the transport's timer runs and, in an export, every 25 ms of audio. A rebuilt channel or rack takes over the curves of the one before and replays them. Inside the voice, the source's FM amount and pulse width and the filter's cutoff, resonance and drive move in the notes already sounding (the filter through its own `ramp`); every other parameter of the source, the play settings and the amp envelope reaches the notes that start after the point, which read the curve at their start. A note's locks of parameters inside the voice are laid over the stored and automated values when its voice is built, and automation leaves those parameters of that voice alone. When the song stops (`endAutomation`), every automated parameter glides back to its stored value 50 ms after its last point, and the curves are forgotten. A bus that is not yet built is built when a send to it is automated (`busUsed`).

`engine.setProject(project)` is called on every change of the document. The store is immutable, so the engine compares object identities, applies parameter changes smoothly, and rebuilds only the channels whose structure changed.

The effects (`src/audio/modules/effects.ts`) are built from stock Web Audio nodes, except four made of custom processors, described below. Wherever an effect has a Mix knob, `blend` sums the dry input and the processed signal, crossfaded by Mix (for the delay and the reverb in a sound, the whole dry with the wet added at the Mix level), and delays the dry path by the processing's latency (the drive's oversampling, the compressor's look-ahead) so the two do not comb-filter. A low cut, in the EQ, in the delay's feedback and as the width's Bass Mono, is a high pass with a path of gain 1 around it, crossfaded to the filter when the cutoff leaves its lowest setting, so at that setting the signal passes bit for bit and sounds made before it existed render exactly as before.

The compressor is Chromium's `DynamicsCompressorNode` with a 6 dB knee. That node turns its output up by itself, by an amount that depends on its threshold and ratio and jumps whenever they change, except when its threshold is 0 dB. So its threshold stays there, and the Threshold knob raises the sound into it and lowers it again afterwards by the same gain; turning the knob is then as smooth as any gain change, and the knee is centred on the knob's value. Make-up is a gain after it, and its gain reduction is read from the node for the meter in the unit (`Engine.effectReduction`). The chorus is two delay lines around 12 ms fed with the mono sum and swung in opposite directions by one LFO, and Spread pans them apart. The phaser is a cascade of all-pass biquads with Q 0.5 swept by an LFO (`lfoRate`, so Sync works as it does for the LFO modulator), their corners set once per 128 samples. A loop in Web Audio has to pass through at least 128 samples of delay, which would turn phaser feedback into a comb, so the phaser sums the first four terms of the feedback series instead, A + fb A² + fb² A³ + fb³ A⁴, taken from taps on the cascade; eight stages take every second tap, and a change of stages or feedback only glides the tap gains. The ring modulator is a gain whose gain is a sine, and the width splits the sound into mid and side and scales the side.

Some effects (the delay, the reverb, the compressor, the chorus, the width and the four made of processors) always give a stereo signal. The output's `StereoPannerNode` passes a stereo signal at the centre unchanged but sends a mono one to each side 3 dB down, so a mono sound is 3 dB louder after one of these effects than without it, even with the effect's mix at zero. This has always been so for the delay and the reverb, and the factory sounds are balanced with it.

### Custom processors

What stock nodes cannot do (a loop shorter than 128 samples, sample-level arithmetic, a reverb that holds its tail) is done by AudioWorklet processors, which run in the audio thread and in an `OfflineAudioContext` alike. They live in `src/audio/processors`, plain TypeScript that imports nothing from the rest of the app, because it runs in the AudioWorkletGlobalScope: `processor.ts` is their frame (the scope's globals, a stereo `Processor` base class that hands `render` both input channels, silence when nothing is connected, and stops on any message from the page, and helpers for NaN, denormals and a cubic Hermite read of a ring buffer, whose gain is at most 1 so it is safe inside feedback), and `index.ts` imports every processor into one module. `src/audio/worklet.ts` imports that module with Vite's `?worker&url`, which bundles it into its own script under `assets/` in the build and serves it as a transformed module from the dev server, the vitest browser project included; Electron serves it over `app://` as `text/javascript`.

`loadProcessors(ctx)` adds the module to a context once and remembers the promise; it resolves to false, with a warning in the console, when the module cannot be added (an insecure page has no `audioWorklet`). `processorEffect(name, values, targets)` makes an `EffectBuilder` of one processor, so such an effect works anywhere a stock effect does. Every processor parameter is driven by a `ConstantSourceNode` whose offset the knob glides and modulators add to (the processor's own parameters stay at 0), so modulation targets exist from the moment the effect is built. Until the module is in the context the effect passes its input straight through; when it arrives the processor is put in its place, and if it never does the effect stays a pass-through. Loading starts with the first such effect built in a context, and `Engine.ready()` waits for it, so an export, an audition or a test renders with every processor from its first sample. The live context loads the module as soon as it is created, the transport starts once that is done, and if it fails the status bar says so in place of Ready. Processors allocate nothing in `process`, read their parameters per frame (knob changes arrive as glides), set NaN and infinite input to 0, and flush tiny values in feedback to 0. When its channel goes, or a rack is rebuilt around it, an effect stops its constant sources and tells its processor to stop once the old graph has faded out. Effects in the racks of the buses and the master are built in `Engine.setProject` like those of the sounds, so the engine's wait covers them too.

The crusher holds each sample until the next one is due at its rate (which modulators move in cents) and rounds it to 2^(bits - 1) steps a side; 16 bits at the full rate is the input, bit for bit. The comb is a fractional delay of one period, read with Hermite interpolation, fed back through a one-pole low pass (Damp) whose phase delay at the pitch is taken off the delay so it stays in tune; its wet output is scaled by sqrt(1 - feedback²), which keeps a broad sound equally loud at any feedback. Space is an eight-line feedback delay network (Jot's design) mixed by a Hadamard matrix, after four Schroeder all-passes on each side: every pass each line goes through a one-pole low pass at Tone and a gain that makes the tail fall 60 dB in Size, its input is scaled by sqrt(1 - gain²) so an impulse leaves the same energy whatever the size, and slow sines swing the line lengths by 0.35 ms. In a sound its Mix adds the wet sound to the dry one, as the Reverb's does. Freeze makes the loop lossless and shuts its input, so the tail holds while new notes play dry on top. Shimmer band-passes the tail between 120 Hz and 6 kHz, shifts it an octave up with two crossfaded grains read at double speed, and feeds it back into the lines through a soft limiter; the band keeps frequencies that the shift would leave in place or fold back down from building up round the loop. The tape records through a tanh saturation, plays back from a delay of 6 ms swung by two slow sines (wow, up to 1.2 % of pitch) and two fast ones (flutter, up to 0.3 %), whose amounts follow their knobs over 0.3 s so turning them bends the pitch no more than the wander does, adds hiss that follows the input's level and is gone a moment after the sound, and rolls off the highs with two one-pole low passes (Age).

The sampler's Crossfade needs no processor: a looped region with a crossfade plays from a buffer of its own (`seamlessLoop` in `src/audio/samples.ts`, kept per buffer, region and share), the region shortened by the crossfade with its end blended into its beginning by an equal-power fade. At 0 the sampler plays the original buffer as before.

The sampler's slices are worked out in `src/core/slices.ts`, which knows nothing of Web Audio, and fetched for a buffer by `sliceTimes` in `src/audio/samples.ts`. Equal slices cut the region evenly. For Hits, `detectOnsets` measures the level of the mono mix on a hop of 0.7 ms twice, once as it is and once on its first difference, which weighs the highs, each as the ratio in dB of the mean power just after a point to that just before it: over 10 ms after and 20 ms before for the full sound, so a low note does not rise and fall with its own period, and over 2 ms after and 6 ms before for the highs, which pin a hit to within a hop or two of where it starts. The larger of the two is the rise at that point; a hit is the latest of the highest rises within 25 ms on either side that is at least 3 dB, and anything starting more than 50 dB under the loudest moment is ignored. The hits of a buffer are found once and kept with it, which takes some 15 to 25 ms for ten seconds of stereo; Sensitivity only chooses among them, needing a rise from 24 dB at 0 down to 3 dB at 1 in equal ratios (8.5 dB halfway), and a hit within 10 ms of the region's ends makes no slice. A note from C3 up plays slice note - 60 as a region of its own at the sample's own rate, so Pitch and Fine still move it and pitch modulators still bend it, but glide does not, since a slice does not follow the key; Loop, Reverse and Crossfade work on the slice as they do on the region. A note below C3 or past the last slice is silent. `sliceNotes` lays the slices out as notes at the tempo and the pitch rate, each on the nearest step from tick 0 and lasting until the next, and the command `slicesToTrack` in `src/app/commands.ts` puts them into the channel's row with the store's `replaceRow`, which replaces the row and lengthens the block in one edit, so one undo takes it back.

Grains is a source made of a processor (`src/audio/processors/grains.ts`), one per voice. A sample's channels reach the audio thread once per context: the first grains voice in a context that plays a sample passes its `Float32Array`s in `processorOptions` (structured clone copies them), the processor files them in a map in the worklet's global scope under the sample's content id, and every later voice in that context passes only the id; the page remembers per context which ids it has sent. The processors of a context share that one copy, and the offline context of an export gets its own. The voice's gate is a `ConstantSourceNode` into the processor's `gate` parameter; it is the voice's first node, so the channel stops it at the end of the release like any source and the processor ends with it, which is why the cloud keeps going through the release. While the gate is open a new grain starts every size / density frames, so Density is the number of grains sounding at once (0.25 to 60), and the level is scaled by 1 / sqrt(0.375 density), the power of that many raised cosines, from two grains up. When the gate opens the processor starts the grains that would already be sounding had it been running for a while, so a note sounds in full from its first frame. Each grain reads a stretch centred on Position, moved by up to half of Spray either way and kept inside the sample, at the note's speed (key tracking from C3, Pitch and Fine as `detune`, so glide and pitch modulators move every grain) times its own random detune from Pitch Spray, rounded to whole octaves with Octaves, sometimes backwards, through a raised-cosine window read from a table of 8192 points, and is panned at equal power by a random amount up to Width. Samples are read with linear interpolation, as `AudioBufferSourceNode` does. The random numbers come from mulberry32 seeded with the voice's `serial`, so an export sounds the same every time and two notes differ. The voice has the same `targets` and `followers` as other sources, with `position` and `spray` as modulation targets, and turning a knob glides the processor's parameter. There are at most 64 grains a voice, all in typed arrays made in the constructor, so `process` allocates nothing. A grain costs about 11 ns a frame on a 2017 Xeon; eight voices of about sixty grains each render some three to four times faster than real time there. Until the processors are in the context a grains note is silent; `prepareSource`, called when a channel's graph is built, starts loading them as soon as a grains sound appears, and `Engine.ready()` waits for that load as it does for the effects, so an export plays its grains from the first note.

The two factory sounds that play recordings, Cloud Pad and Chopped Break, carry no audio in their preset files. `src/presets/samples.ts` synthesises the recordings when they are first needed (a one-bar break at 120 BPM at 44.1 kHz and six seconds of a detuned Dm9 pad at 22.05 kHz, each some 80 to 100 ms of work), encodes them as 16-bit WAV, and gives them fixed content ids that a test checks against their content. `preset` sets the sample id and `presetSamples` hands over the sample data, so a factory sound is added to a project with its sample like a sound from the library.

The engine takes any `BaseAudioContext`. The same code plays live through an `AudioContext` and renders an export through an `OfflineAudioContext`. An export that rings out renders on after its last note for `ringOut` in `src/audio/render.ts`: for every sound 1.25 times its release (when the release reaches silence), then each reverb's size, each delay's time and each comb's period multiplied by the repeats their feedback takes to fall by 80 dB (a low cut or damping only shortens that), Space's size times 4/3 and once more with full shimmer, and the short tails of the effects without feedback (`SHORT_TAILS`: the chorus's longest delay, the compressor's look-ahead, 0.25 s for the phaser's all-passes and 1.5 s for the tape's hiss to fade), the longest of the sounds, then the same for the longest-ringing bus that is sent to and for the master rack, at least 6 s and at most 60 s. A frozen Space rings for ever, so a sound, bus or master with one always gets the longest tail, 60 s. The silence at the end is trimmed off afterwards, so a long estimate costs only rendering time.

Stems (`renderStems`) are one render for each sound the mix lets through (mute and solo as they are) that has notes in the scope, each the whole project with only that sound soloed. So a stem goes through the same graph as in the mix, its effects, the master level and the soft clipper included, and keeps working when shared buses arrive. The renders get the tail of the whole project and are padded with silence to the longest, so they line up. Because the clipper is not linear, stems added together can differ slightly from the mix.

The metronome (`src/audio/metronome.ts`) is a small look-ahead scheduler of its own beside the transport. It reads the transport's clock and clicks a short sine on every beat that `beatsBetween` in `src/core/meter.ts` finds, higher on the downbeat, straight into the context's destination, so it never passes the master and never exists in an offline render. Without the metronome switched on it still clicks the beats before tick 0, which is the count-in.

## Time

The sequencer in `src/core/sequencer.ts` is a pure function from a project, a play scope (one block on repeat, or the song) and a range of ticks to a list of note events with times in seconds; every note that starts in the range is in it once. `heardAt` tells which blocks are heard at a tick, which is also how the views place their play markers. The transport calls it a little ahead of the audio clock (a look-ahead scheduler), one step's window of ticks at a time, through `playStep` in `src/audio/transport.ts`, which hands the events to the engine with `playEvent`; the offline renderer goes through `playStep` too, step by step a chunk ahead of the render, so an export schedules exactly what live playback does. The transport's `clock()` is the context time of tick 0 with the tempo and swing it counts in; a count-in starts the transport with tick 0 one bar later, so the bar before it has negative ticks. `outputDelay` is how long sound takes from the context's clock to the speakers (the context's base latency plus the device's output latency), and the playhead and recording both subtract it. A step is a sixteenth note, and a bar has as many as the meter says. Swing delays every second sixteenth by up to half a step: `tickTime` stretches the first step of each pair and squeezes the second, and moves the ticks inside them in proportion, so notes on the grid play exactly where the swung steps fall and notes between grid lines keep their relative place. Every meter has an even number of steps to the bar, so the pairs start again with each bar. A note's end is placed the same way as its start.

The extras are played here too. Whether a note with a chance plays on a pass is `plays`, a hash of the note's id, the block's id and the pass, so every play and every export sound the same: in the block on repeat the pass counts how often the block has started since playback began, in the song it is the bar where that repeat of the placement starts. A ratchet becomes that many events evenly inside the note's length, at fractional ticks that go through the same swing; repeats past the end of the block or the placement are left out, and with a chance the whole ratchet plays or none of it. A held note is started only by the first repeat of the block in its placement and lasts to the placement's end, or to the end of the block on repeat; its length is worked out in ticks and turned into seconds like any other. A slide is passed on as `NoteEvent.slide` on the first event of the note; the engine decides what to do with it.

A row with a loop of its own plays, in every repeat of its block, copies of its loop from the block's start, as many as begin inside the block; the last may be cut short, and a ratchet repeat past the end of its copy is left out. Every row starts again with the block, also in the song, where a placement repeats the block as a whole. Swing counts from the bar, as for every other note, so a copy that starts on an odd step is swung there and a note always sounds where its step sounds in every row. A chance is decided anew in each copy: the first keeps the block's pass, the others ask `plays` about the pass followed by the copy's number.

The arpeggiator is part of a sound's play settings (`play.arp`, `rate`, `octaves` and `gate` in `PLAY`), and `arpOf` turns them into ticks. `arpeggiate` in `src/core/arp.ts` takes the notes held, each from a start to an end tick, and plays them one after another: whenever the set of held notes changes (a note starts or ends) the order starts again at that tick, with a note every `rate` ticks for as long as the set stays, each `gate` of the rate long and never longer than the note it plays. `arpOrder` gives the order: lowest first over the octaves for Up and Random, its reverse for Down, up and back without repeating the ends for Up-Down, and by start for As Played. Random picks each note by a hash of the keys of the held notes, where the set began and the step. The answer for a window depends only on the held notes, so windows that meet give each note once. For a sound whose arpeggiator is on, `eventsBetween` hands it the row's notes as they sound in the pass (copies of a row's loop and hold notes included, each cut at the end of the block on repeat or of the placement), looking back as far as a note that can still sound or that changed the held set last, and turns what it returns into events through the same swing as any note. Each of these notes takes the slide of its note and asks the chance of its note anew, with the pass followed by its place in that note; ratchets are ignored. The engine only sees more, shorter notes.

The mix of the song is played here as well. A muted lane, or one at the bottom of its range, gives no events, and neither do the channels a placement mutes. Every note of a placement that has a fade, or that sits in a lane not at 0 dB, gets a gain curve from `noteCurve` in `src/core/arrangement.ts`: the fades are equal-power curves (the sine of a quarter turn), sampled at seventeen points each, multiplied together and by the lane's gain, and turned into seconds through the same swing as the notes. A note's curve runs from its start to its end, and on to the end of a fade it ends inside, so its release rises or falls with the fade; a note still sounding when a fade-out ends is silent from there. Notes that meet no fade get a single point. Everything happens before the engine, so live playback and export sound the same, and a change of lane level or fade reaches the notes scheduled after it, not those already sounding.

Automation is worked out here as well, by an `Automator` (`src/audio/automator.ts`) that the transport makes when the song starts and the renderer makes for an export of the song; a block on repeat has none, so it plays its stored values. `start` sends every automated parameter to its value at the starting tick, so playback from any point begins with the right values. `playStep` first gives the automator the step's notes, whose locks of shared parameters it holds from the note's start to its end (`hold`), and then the step's ticks (`advance`). It samples every followed parameter on a grid of three ticks (`AUTO_GRID`, a 32nd triplet): the latest lock sounding then, else its row, else its stored value. A point goes to the engine only where the value changes, together with the sample before the change when the value held until then, so straight segments arrive as straight ramps, a held value costs nothing, and the end of a lock falls back within one grid step. Times go through `tickTime`, so automation swings with the notes. The renderer and the transport call the same code with the same project, so their points are the same (a test compares them).

## Playing in

Notes played by hand (the computer keyboard, the Factory's piano, MIDI) all go through `noteOn` and `noteOff` in `src/app/audio.ts`, which tell `onLiveNote` listeners the context time they happened at. MIDI (`src/app/midi.ts`) asks for `requestMIDIAccess` without system exclusive messages, listens to every connected input and follows inputs that come and go; each input keeps the sound each of its notes started on, so a note-off reaches it after the selection changed, and its sustain pedal holds the notes let go until it rises. Notes played by hand on a sound whose arpeggiator is on are not given to the engine as they are: `LiveArp` in `src/app/arp.ts` keeps the keys that are down, each from the tick it went down to the tick it came up, runs `arpeggiate` over them every 10 ms and hands the engine the notes due in the next 30 ms. It counts ticks on the transport's clock when the transport runs as the first key goes down, else on a clock of its own at the project's tempo and swing that starts with that key, and keeps that clock until every key is up, so its notes lie on the same grid as the block's while the block plays. A key going down or up starts the order again at once. `onLiveNote` listeners still hear the keys, so recording writes what was held. A browser lets a page make sound only after a click or a key press, so until then MIDI notes only blink the lamp; the Electron shell allows sound at once.

Recording (`src/app/record.ts`) runs while Record is on and a block plays on repeat. A key that goes down is placed at `heardTick`: the context time minus `outputDelay`, on the transport's clock, through `timeTick`, the inverse of the swing warp in `tickTime`. So a note is written where the loop was heard when it was played, and plays back there. When the key comes up, `takeNote` in `src/core/record.ts` turns the two ticks into a note of the block: with Quantize the start goes to the grid line that sounds nearest (lines restart with every bar, and with swing the nearest by `tickTime`, not by drawing), and the length to whole grid units, at least one; the block repeats from tick 0, so the start wraps into it, and a note held past the block's end is cut there. Notes that start in the count-in, before tick 0 after quantizing, are dropped. Stop or Record off writes the keys still down as if let go then. Stopping, or switching to the song, turns Record off.

## Undo

The store keeps up to 100 earlier projects. A change normally is one undo step; changes with the same key less than 800 ms apart (a knob being turned, a name being typed) are merged. Automation's points are part of the document like anything else, so adding, moving and removing them is undone; the values automation gives parameters while the song plays never are, since they are not in the document. A pointer gesture in the views (painting cells, dragging a note or a placement) calls `beginGesture` when the button goes down and `commitGesture` when it comes up, and everything the store changes in between is one undo step however long the gesture takes. Actions that are one gesture on their own, such as `duplicatePlacement`, change the document once. A recording pass writes each note with `addNotes` and its pass as `take`, and the Randomise dialog its results with `replaceNotes` and a take of its own; a change of the same take joins the undo step of the one before as long as that is still the document, so a pass is one undo step unless something else is changed in the middle of it, which starts a new one.

## The shell

The Electron main process creates a frameless window (the retro title bar in the page is the real one), serves the built app from an `app://` origin, and answers a small set of requests from the page: open and save dialogs, the sound and block library folders (`Documents/Hadjitron 3000/Sounds` and `Blocks`), window controls. For stems the page asks for a folder (`folder-choose`, which shows a folder dialog and hands back a number for it) and then writes into it by that number (`folder-write`), only plain file names ending in `.wav` or `.mp3`, and only into folders the user picked. The session grants MIDI to the app's own origin and refuses every other permission; Electron names even a request without system exclusive messages `midiSysex`, so both MIDI names are answered alike. Every page the app tries to open in a window of its own is refused (web links go to the browser), except the Guide Book's: a blank page named `guide-book`, one at a time, which gets the app's icon, the title Guide Book, no menu bar, a minimum size and a frame like the main window's, may not navigate or open windows itself, and is closed when the main window closes, reloads or its page dies. The page only sees the `Platform` interface in `src/platform/api.ts`; in a browser the same interface is backed by file pickers, downloads and IndexedDB.

On Windows the shell differs in a few places, and nowhere else does the code ask which system it runs on. The native menu is removed (`Menu.setApplicationMenu(null)`), so Alt brings up nothing; the page draws the only menu bar, and File ends with Exit and the system's Alt+F4 where a Mac has Quit. The frameless window keeps Windows' own behaviour for the title bar the page draws, since its drag region counts as the caption: double-click to maximise, drag to an edge to snap. The minimise, maximise and close buttons are the page's own, in the Windows order at the right, so Windows 11's snap layouts flyout on the maximise button cannot appear. A file double-clicked in Explorer arrives as an argument, either to a new process or, through the single instance lock, to the running one (`second-instance`), where macOS sends `open-file`. The process takes the application id `com.hadjitron.app`, the id of the installer's shortcuts, so a pinned taskbar button and the running window are one. Library names Windows cannot store (`<>:"|?*`, a trailing dot or space, CON, NUL and the other device names) are refused with the same message as a slash, and a name suggested to the save dialog has those characters replaced by dashes (`validateLibraryName` and `suggestedName` in `electron/paths.cjs`, both given the platform); stem names avoid them everywhere. The libraries stay in Documents, where `app.getPath('documents')` finds the folder also when it is redirected, and `update.log` and the browser storage are in `%APPDATA%\Hadjitron 3000`. Keyboard shortcuts take Ctrl instead of Cmd; their labels are pure functions of the platform in `src/app/shortcuts.ts`, tested for both. The pixel fonts are bundled, the files the app writes are made by the page with `\n` line endings, and `.gitattributes` keeps every checkout in LF, so the tests read the same bytes on Windows.

The open project and the view it was shown in are kept in IndexedDB a second after every change (`src/app/session.ts`) and restored on the next launch. The first launch opens the demo song in the Song view.

## Factory material

The factory sounds are `.h3s` files in `src/presets/sounds`, bundled with `import.meta.glob`; `PRESET_GROUPS` in `src/presets/index.ts` lists them in the groups and order of the Sound Library, and a file that is not listed there is not offered. Each writes only the parameters that differ from their defaults, as a hand-written file would, and none carries sends or ducking, which belong to a project's channels. None carries a sample either: Cloud Pad and Chopped Break play recordings made in code (`src/presets/samples.ts`), which `preset` points them at and `presetSamples` hands over with them, into a project's samples as the Ambient example takes Cloud Pad's. The demo (`src/presets/projects.ts`) and the six examples (`src/presets/examples`, one module per song, listed in `EXAMPLES`) are projects written as code with the small helpers of `src/presets/compose.ts`: channels of factory sounds, drum rows written as strings, melody rows and chords as lists, blocks, lanes with fades and silent sounds, the sends and ducking of the mixer, and locks and rows of automation given in the units of their controls (`lock`, `automate`), which turn them into knob positions through the control's taper. Notes go through `cleanNotes`, so a project built this way is exactly what the file reader would make of it. `factoryBlocks` takes the blocks of the demo and of every example out of their projects with `extractBlock`, so the Block Library always offers what the songs play. File, Open Example builds a fresh copy of an example (`openExample` in `src/app/commands.ts`), opens it without a file, after `confirmDiscard`, and shows the Song.

`tests/unit/presets.test.ts` checks the material as data (every file listed once, round trips, block and song structure, valid mixers and lanes), and `tests/browser/presets.test.ts` renders every sound and checks it by numbers: a peak below the clipper and above silence, a level within 2.5 dB of the sound it is balanced against over its first half second (pads, drones and risers within 3 dB of Warm Pad after they have swelled, at 8 kHz), a spectral centroid in the band of its kind, and for the risers a brightness that moves the right way. The examples are rendered at a reduced sample rate to keep the browser tests quick: each must stay clear of the clipper, be loud enough and render the same twice.

A library block is auditioned by rendering it offline on its own, at the tempo of the open project, and playing the result once (`auditionBlock` in `src/app/audio.ts`); it never enters the live engine or the project.

## The Guide Book

The Guide Book lives in `src/app/book`, and its chapters are data. Each chapter is one file in `src/app/book/chapters`, named with its number so the files sort in reading order, whose default export is a `Chapter`: an id, a title and pages. `pages.ts` gathers them with `import.meta.glob`, so adding a chapter is adding one file, and defines the pieces a page is made of: a paragraph is a plain string; `example` is something to hear and load, optionally with a live scope or envelope picture drawn by the app's own displays; `compare` is a before and after pair with the difference it claims, named as a measure (brighter, more lows, a longer tail, wider, and so on); `knobs` is a table generated from the module's definition in `src/core/modules.ts` and its hints, with one sentence of the book's own on when to reach for it; `envelope` draws an amp envelope; `terms` is a glossary list; and `worked` is a set of guided steps from an example to a stated result, with checkpoints for the recipes. Longer chapters can keep their pages in a folder of their own, as the recipes do in `chapters/recipes`; only files directly in `chapters` are chapters.

Examples are built in code (`build.ts`): a sound from a factory sound or from nothing, notes, blocks and whole projects, with fixed ids so they render the same every time; a project whose sounds play the factory pad or break carries that recording in its samples, and an example song from `src/presets/examples` is used as it is. A sound example joins the reader's project, a block example adds its block, and a project example replaces the project after the offer to save. The steps of a worked example are made by the helpers in `steps.ts` from what they change (`set('fx:delay', { mix: 0.2 }, text)`, `addMod('lfo', text)`, `write(block, sound, notes, text)`, `place(...)`, `duck(...)`, `lock(...)` for a note's own knob value, `automate(...)` and `curve(...)` for a row of automation, and so on), so each step knows the control it points at, the folded sections it needs open in beginner mode, how to tell it is done (a knob counts within a twentieth of its travel) and how to do it; the finished example is its start with every step's action done, and a checkpoint is the start with the steps before it done. `bookStore.ts` turns pages, remembers the page in the preferences, loads examples and plays them without loading them, by rendering offline and playing the result (`playRendered` in `src/app/audio.ts`, which block audition uses too); while a long example renders, the book shows how far it has got, and Stop gives the render up. `Book.tsx` draws the book as a panel docked at the right of the views, with the contents beside the page.

Detached, the book lives in a window of its own, drawn by the same renderer from the same stores. `bookWindow.ts` opens a blank page of the app's origin with `window.open('', 'guide-book', ...)` at the size and place the preferences remember (`bookWindow`, the inside size and the screen position, saved on every resize and when the window closes), then clears the window's name so no other `window.open` can reach it. It copies the app's `<style>` and stylesheet `<link>` elements into the window's head under a `<base>` of the app's address, so the fonts load from the same place, and copies them again whenever they change in the app's head, which is how Vite's updates reach the book in development. It installs the app's keyboard handler (`installKeys` takes the window) on the book's window, so Space, Undo and the rest work there, and before it a handler on the book's document that keeps the arrows, Page Up and Down, Home and End for scrolling the page, unless the contents list has used them. `Book` then renders the panel into the window's body with `createPortal`; React listens for events on the portal's container, so the handlers work as they do docked. The panel gets a status bar of its own for the hints, its title bar follows that window's focus, and while a dialog of the app is open the book's body is inert, as the docked book is under a dialog, and the main window takes the focus and gives it back afterwards. Closing the window (`pagehide` in it) closes the book, and the app's own `pagehide` closes the window. If `window.open` gives nothing, as behind a pop-up blocker, the book stays docked and says so in the status bar. What had to change for drawing into another document: the kit's `Display` takes its animation frames from the window its canvas is in, since a window in the background slows its own frames down; the keyboard handler recognises text fields by tag name, since elements of the book's window are not instances of the app window's classes; and the book's media queries are answered by the window they are in, so the detached book has rules of its own and fills its window.

Guided steps run in `src/app/tour`. `tourStore.ts` keeps the running steps, shows each step's view, sound, block, piano roll and folded sections, and `Tour.tsx` draws the frame around the target, found by the `data-tour` attribute the views put on their controls (the kit's Button, TextField, RackUnit, Tabs and MenuBar pass it through), measuring it on every animation frame so that the frame follows it, cut to the boxes that scroll around it, and scrolling it into view when it appears or when the app moves it out of view, though not when the user scrolls it away; automation rows are `auto-1`, `auto-2` and so on, in the order of the rows; the step's words and buttons are in the book. On the very first launch `restoreSession` reports that no session was ever stored, remembers that in the session store, and the app shows a welcome window once, which offers the demo, the first two lessons and the book.

To add a chapter, add a file to `src/app/book/chapters` with the next number and a default export of a `Chapter`. The unit tests in `tests/unit/book.test.ts` check that it parses, that its knob tables name real modules, that its examples are valid projects and that every worked example can be done step by step; `tests/browser/book.test.tsx` checks that every step's control is on screen in beginner and pro mode, and `tests/browser/bookaudio.test.ts` renders every example, measures every pair for the difference its page claims, and checks the recipes for level and determinism.

## Adding a module

1. Add its definition to `SOURCES`, `EFFECTS` or `MODS` in `src/core/modules.ts`, with a level for it and each parameter, and a hint for each parameter in `src/ui/factory/hints.ts`.
2. Add its audio in `src/audio/modules` and register it there.
3. Add a preset that uses it and a test in `tests/browser`.

The Factory shows the new module with a generic panel built from its parameter list. A custom panel is only needed when the module wants a special display.

An effect that needs custom signal code is a processor. Write it in `src/audio/processors` as a subclass of `Processor` with `static parameterDescriptors = params(...)`, its own `render` and a `register('name', Class)` call, and import it in `processors/index.ts`. Its builder in `effects.ts` is one call, `processorEffect('name', (p) => ({ ... }), targets)`, which maps the module's parameters to the processor's and names the processor parameter each modulation target moves; a target in cents is a separate `detune` parameter at 0. If it rings on, give `ringTime` in `render.ts` its tail. Test it in `tests/browser/processors.test.ts` like the others there: what it does, that turning its knobs does not click, and that silence, DC and NaN come out as silence, finite and finite.

## Updates

Help, Check for Updates talks to one `Updates` interface (`src/platform/api.ts`) with two implementations, and the main process picks one when it starts: the self-building one when `electron/install.json` is packed into the application (a Mac, built from a checkout), the release one in a packaged application on Windows without that file, and none in development. The page learns which from `--hadjitron-updates=source` or `=release` among the window's arguments, and `UpdateDialog` is one component that words the two differently: a build from source counts commits and builds; a release names versions and downloads. Both report progress as a step and a fraction of the whole, and a failure ends in the dialog's failed state with a sentence, the current version still running. The details go to `update.log` in the user data folder.

`npm run app` (`scripts/install-app.mjs`) writes `electron/install.json` before packaging: the checkout's path, the shell's PATH and the commit being built. The file is packed into the application and removed from the checkout afterwards. `electron/update.cjs` compares the built commit with the checkout's upstream after a `git fetch`, and to update runs `git pull --ff-only`, `npm install` and `install-app.mjs --build-only` in the checkout. On restart a detached shell waits for the old process to exit, moves the new bundle over the old one and opens it.

The Windows application is installed from `Hadjitron-3000-Setup-<version>.exe`, a per-user NSIS installer made by electron-builder (`electron-builder.yml`: Start menu and desktop shortcuts, an uninstaller, the three file types, the icon `build/icon.ico` that `scripts/make-icon.mjs` makes from `build/icon.png`). Its `publish` entry names the GitHub repository, which makes electron-builder write `latest.yml` next to the installer and `app-update.yml` into the application. `electron/release.cjs` wraps electron-updater (a dependency, so it is packed): it never downloads or installs on its own (`autoDownload` and `autoInstallOnAppQuit` are off), and with `fullChangelog` the check returns the notes of every release newer than the running one, which arrive as HTML and become plain lines. Building downloads the installer with its progress events; restarting closes the window as usual, offering to save, and on `will-quit` hands over to `quitAndInstall`, which runs the installer with its progress bar and opens the new version. Errors become sentences in `readableError` (offline, GitHub failing, no release yet, no Windows installer in it, a damaged download, a full disk). The installer is not signed, so electron-updater has no publisher to check it against.

Nothing under Documents or the user data folder is part of the application, so updates never touch the user's files.

## The workflow

`.github/workflows/build.yml` runs on a pushed tag `v*` (a release), on a pushed tag `ci-*` (a test build) and by hand. Two jobs run side by side with the built-in token reading only. Windows: install packages, typecheck, unit, browser, build, the end-to-end tests, package the installer, install it silently, run the Electron end-to-end tests again against the installed program (`HADJITRON_EXE`), uninstall it, and keep the installer, its blockmap and `latest.yml` as an artifact. `scripts/ci-windows-install.mjs` checks what the installer did: the program under `%LOCALAPPDATA%\Programs`, the uninstaller, `app-update.yml`, both shortcuts and the three file types, and after uninstalling that they are gone. macOS: the same tests and the disk image. On a `v*` tag both jobs first check that the tag is `v` plus the version in `package.json`, and after both pass a third job, with permission to write releases and nothing else, publishes the release named after the tag with the installer, its blockmap, `latest.yml` and the disk image, and notes made from the commit subjects since the previous `v*` tag. Every test step runs through `scripts/ci-step.mjs`, which on a failure writes the most telling lines of the step's output as error annotations, readable from the public API without logging in, and its last lines into the job summary. Timing-sensitive tests get one retry on CI (`retry` in `vite.config.ts`, `retries` in `playwright.config.ts`).
